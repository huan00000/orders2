# Orders2 C++ 容器化产品企划书

## 一、项目目标

将现有 Orders2 脚本统一迁移为 C++，打造一款**在 Armbian 上运行、通过 Docker Compose 启动、使用 TUI 操作的容器化产品**。

可以把它想象成一个“装进容器的终端控制台”：用户拉取镜像、启动容器，即可在终端中查看信息和执行操作，无需自行编译。

## 二、改造范围

- **迁移对象**：`E:\git\0AAimportant\gate_bot\ago\v3\auto_orders\tests\orders2` 中的现有脚本。
- **技术统一**：业务逻辑与运行入口改用 C++，源代码采用 `.h`、`.cpp` 等文件，通过 CMake 管理构建。
- **功能延续**：梳理现有脚本的功能、配置和调用关系，逐项迁移，保留原有核心行为；相关测试同步迁移。
- **操作入口**：以 TUI（终端文字界面）集中呈现功能，让用户在一个控制台中完成查看与操作。
- **文件归档**：迁移后的源码、构建文件、容器配置及文档统一放入 `c` 目录。CMake、YAML 和 Dockerfile 作为必要的构建与部署配置保留。

目标目录：`E:\git\0AAimportant\gate_bot\ago\v3\auto_orders\tests\orders2\c`。

## 三、构建与交付方式

**现有脚本 → C++ 程序与 TUI → GitHub Actions 编译、测试 → 构建并发布镜像 → Armbian 上用 Docker Compose 启动。**

本地只进行代码编写与检查，**不执行编译**。编译、测试及镜像构建统一交给 GitHub Actions。

容器镜像内包含适配目标 Armbian 设备架构的可执行程序及运行依赖；具体支持的 ARM 架构在实施前确认。

镜像交付形式参考：[Orders2 容器包](https://github.com/huan00000/orders2/pkgs/container/orders2)。

## 四、主要交付物

| 交付物 | 用途 |
| --- | --- |
| C++ 源码与测试 | 承接原有脚本功能，提供统一 TUI 入口 |
| `CMakeLists.txt` | 统一管理编译与依赖 |
| `.github/workflows/build.yml` | 在 GitHub Actions 中自动编译、测试、构建和发布镜像 |
| `Dockerfile` | 将程序及运行依赖封装成容器镜像 |
| `compose.yml` | 提供可直接使用的部署配置，并配置 TUI 所需的终端输入支持 |
| 配置示例与使用说明 | 说明配置填写、启动、进入 TUI、退出和升级方法 |

**工作流放置要求**：GitHub Actions 只识别仓库根目录下的 `.github/workflows/`。如果 `c` 作为独立仓库发布，工作流可完整保留在 `c` 内；如果沿用当前仓库，则需在当前仓库根目录部署工作流，并让其构建 `c` 中的项目。

## 五、实施步骤

1. **摸清现状**：建立脚本与功能清单，确认配置格式、外部依赖及目标设备架构。
2. **完成迁移**：按模块改写为 C++，接入 TUI，核对迁移前后的功能行为。
3. **打通交付**：配置 CMake、GitHub Actions、Dockerfile 和 Docker Compose，生成可拉取的镜像。
4. **实机验收**：在目标 Armbian 设备上验证启动、终端交互和主要功能，补齐使用说明。

## 六、验收标准

- 原有脚本功能有对应的迁移清单，核心功能验证通过，运行不再依赖原有 Python 脚本。
- GitHub Actions 能完成编译、测试及镜像发布，全程无需本地编译。
- 镜像适配目标 Armbian 设备，用户可按文档通过 Docker Compose 启动并进入 TUI。
- TUI 显示正常，键盘输入有效，主要操作可完成，程序可正常退出。
- 源码、配置与文档按约定归档，用户能够照着说明完成部署。

最终交付的是一套**源码可维护、云端可构建、镜像可部署、终端可操作**的完整产品。
