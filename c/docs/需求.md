## 三、仓库、构建与发布

- 将 `c` 目录作为新的独立 GitHub 仓库发布。
- GitHub Actions 工作流位于该独立仓库根目录的 `.github/workflows/`。
- 本地只编写和检查代码，不执行编译；编译、测试、镜像构建和发布统一由 GitHub Actions 完成。
- 主分支每次通过检查后发布镜像。
- 设备由用户手动升级，不自动更新运行中的版本。
- 手动升级前必须彻底停止所有任务，再备份和升级；升级后由用户手动启动任务。停止仍按第四节规则撤销任务挂单并保留持仓，升级后启动涉及遗留持仓时仍需确认接管。此升级流程不采用保留运行状态后自动恢复的方式。
- 先完成本地交付文件，实际发布前再确认新仓库名称和镜像地址。企划书中的容器包链接仅作为交付形式参考，不视为已选定的新发布地址。
- 主分支通过检查后，同时发布 `latest` 和对应提交的 SHA 标签，支持按提交选择版本。

## 四、后台运行与 TUI

- 业务任务在后台持续运行，TUI 可独立退出并重新连接。
- 关闭 TUI 或断开 SSH 不应导致业务任务停止。
- TUI 提供完整管理入口：账户配置、参数编辑、任务启动、暂停和停止、状态与数据查看、日志查看以及交易操作。
- TUI 应提供清晰的后台运行状态，让用户在重新连接后能够查看和管理已有任务。
- 退出 TUI 与停止后台任务是不同操作，界面应明确表达其作用。
- 新终端连接 TUI 时接管控制权，旧终端转为只读。
- 后台服务与 TUI 的具体进程结构及通信方式待实施细化。
- 支持多个后台实例，各实例使用独立数据库；同一账户只由一个实例管理。第一版自动阻止同一宿主机内重复管理同一账户；跨设备由用户保证不重复。账户归属配置、账户识别及同宿主机互斥实现待细化。
- 按“账户 + 交易品种 + 多空方向”划分任务。同一账户、同一品种、同一方向最多允许一个活动任务，其他任务拒绝启动。运行、暂停、处理中及等待人工处理均占用活动任务名额，只有彻底停止后才释放。
- 用户主动暂停：停止新增交易操作，保留挂单、持仓和原目标，继续查询状态。异常暂停仍遵循第七节已确认规则。
- 暂停期间保留的挂单发生成交时，更新订单和持仓记录，保持暂停，恢复后再决定下一步操作。
- 任务运行中，用户在交易所手动交易导致同品种、同方向持仓变化时，更新实际持仓记录并暂停该任务，由用户确认管理范围后恢复。
- 用户主动停止：撤销能够确认属于该任务的全部未成交订单后结束目标，保留持仓，不自动平仓。
- 停止时部分订单撤销失败，保持“停止处理中”，按第七节已有的 5 分钟核实时限与查询间隔处理；超时转人工，暂不结束目标。此时尚未彻底停止，仍占用活动任务名额。
- 停止过程中订单在撤销成功前发生成交，保留新增持仓，继续撤销剩余挂单，完成后结束目标。
- 已停止任务留下持仓时，启动同账户、同品种、同方向的新任务需展示遗留持仓摘要，经用户确认后将其纳入新目标管理。
- 用户点击暂停或停止时，如已有交易请求发出但结果未确定，界面显示“处理中”，先核实请求结果，再完成暂停或停止；超时转人工处理，沿用第七节的核实时限与查询间隔。

## 五、实盘操作

- 配置有效凭据后即可执行实盘操作。
- 不将每次启动手动解锁、逐笔人工确认或先交付模拟版作为强制启用条件。
- 首次部署且没有可恢复任务时，只启动后台服务，由用户在 TUI 手动创建并启动任务，不自动创建或启动默认交易任务。重启后恢复此前运行任务的规则继续有效。

## 六、配置与密钥

- 沿用现有配置格式，通过宿主机文件挂载到容器。
- 不强制改用新的配置格式、独立密钥文件或环境变量方案。
- TUI 的账户配置与参数编辑需与沿用的配置方案协调一致。
- 运行中任务不允许修改配置，必须先停止任务，再编辑并保存。
- 第三轮确认：后台所有任务停止后，才能编辑任何配置；此规则也适用于多个任务共享配置的情况。
- 保存前检查配置格式与必填项，检查失败不覆盖原文件；先写临时文件，成功后替换原文件，并保留最近 1 份配置备份。
- 具体配置文件清单、挂载路径及配置备份位置待梳理明确。配置备份与任务恢复状态数据库备份分别管理；数据库备份规则见第十三节。

## 七、重启恢复

- 容器重启后自动核对交易所订单与持仓，再恢复此前运行的任务。
- 核对完成前不直接继续执行交易任务。
- 恢复对象为此前运行的任务，不应将此前已停止或暂停的任务自动启动。
- 任务恢复状态及运行日志使用 SQLite 持久化；原有文件位置与格式仍需梳理，以明确迁移关系。数据库默认存放位置和日志保留规则见第十三节。
- 重启核对发现交易所订单或持仓与本地记录不一致时，以交易所数据为准自动修正本地记录，修正成功后恢复此前运行的任务。
- 交易所暂时不可用，或下单请求超时且结果未知时，自动核实时限为 5 分钟；查询间隔依次为 2、4、8、16、30 秒，之后每 30 秒一次。到达时限仍无法核实则等待人工处理。
- 下单结果未知时只查询核实，不直接重复下单；确认未下单成功后，允许任务重新判断是否下单。判定未成功所需的具体证据待实施细化。
- 查询暂时找不到订单但仍不能确认请求失败时，继续按已有规则核实；达到 5 分钟时限后转人工，不将“查不到”直接视为失败。
- 下单结果未知期间，仅异常任务暂停发起新的交易操作，查询、日志及状态显示继续运行。
- 在核实时限内成功核实并修正本地记录后，等待 30 秒再自动恢复异常前正在运行的任务；用户可在这 30 秒内取消恢复。
- 自动恢复倒计时内，用户主动暂停或停止优先：取消倒计时，并执行对应的暂停或停止流程。
- 用户取消自动恢复后，任务保持暂停并保留原目标；用户点击恢复后重新核对，核对通过再继续原目标。
- 超过核实时限并进入等待人工处理后，停止自动核实，由用户手动触发重新核实与恢复。
- 结果未知请求超过 5 分钟转人工后，TUI 只允许重新核实，取得明确结果后才能恢复；不提供手填交易所订单 ID 解除阻塞或人工认定请求失败的入口。
- 重启时任务状态缺失或损坏，从最近一次有效备份恢复，核对交易所后自动恢复此前运行的任务；无有效备份则等待人工处理。
- 交易所数据已查明但本地记录无法修正或保存时，停止该账户全部任务，等待人工处理。此异常处理范围优先于单纯下单结果未知时的单任务暂停规则。第七轮确认：SQLite 无法保存并触发账户全部任务停止时，不发送新交易请求，保留挂单和持仓，尽可能继续只读查询，等待人工处理；不套用用户主动停止时的撤单流程。等待人工处理期间仍占用活动任务名额。
- SQLite 存储恢复正常后，由用户手动触发检查，保存并核对成功后逐个恢复任务，不因存储恢复而自动恢复交易。

## 十三、订单状态机、Intent 与 SQLite

- 用户补充原话：“我还想要订单状态机. Intent. SQLite之类啥的功能”。
- 第四轮确认：订单状态机、Intent、SQLite 全部纳入第一版。
- Intent 同时支持目标意图与操作意图，记录两者关系。第六轮确认：原有订单联动采用一个目标覆盖开仓至最终平仓，开仓、撤单和平仓属于该目标的子操作。每次操作结束后，根据最新订单和持仓情况生成下一步操作；具体拆分算法及完整状态转换待细化。
- 订单状态机管理本程序创建的订单，以及按第十八节规则核对确认的旧版本迁移订单；其他订单仅展示，不自动接管。新程序订单重启后使用交易所支持的客户订单标识，并与本地记录对应以识别归属；无法确认归属的订单只展示，不自动接管。具体标识格式及交易所支持情况待实施核对。
- 状态机包含待提交、已提交、部分成交、已成交、已撤销、拒绝等基本状态，并覆盖提交中、结果未知、撤单中和异常核实流程；保留每次状态变化的时间、原因和来源。
- 第四轮第 5、6 题经补充确认后，采用分阶段保存：执行交易前先在 SQLite 中持久化防重复标识及必要关联信息，保存成功后才能发送交易请求；完整 Intent 和结果仍在执行后保存，供历史查询使用。
- 用持久化唯一 Intent ID 识别重复请求，同一 ID 返回已有处理结果；请求结果未知时继续遵循先查询核实、不直接重复下单的规则。防重复标识及关联信息的具体字段、事务边界和崩溃恢复实现待细化。
- 每个任务最多存在一个未完成的目标意图；该目标下的操作意图逐个执行，同一时间最多存在一个未完成的操作意图。父目标与当前子操作可以同时处于未完成状态，不按两层合计只能有一个 Intent 限制。
- 已有未完成目标时拒绝新目标，当前目标完成后才能提交新目标，不自动排队或替换。
- 目标完成条件沿用原脚本的完成条件，须先梳理成清单，再由用户确认；当前尚未确认具体完成判据。
- 原目标完成后，仍处于运行状态的任务按原策略继续判断，满足条件时自动创建下一目标；仍须遵守每任务最多一个未完成目标的限制。
- 操作意图明确失败（例如下单被拒绝）时，父目标暂停，等待用户处理后继续，不自动重试。结果未知仍按第七节的核实规则处理，不按明确失败处理。
- 明确失败后，用户点击恢复时，重新核对订单和持仓，按最新情况重新计算下一步操作。
- SQLite 保存任务恢复状态、Intent、订单、成交记录、状态变化历史、人工操作记录及普通运行日志。保留现有配置文件格式，不将账户配置及密钥自动迁入数据库。

## 十八、旧版本数据迁移

- 旧 `orderlist.js` 的订单状态通过 TUI 迁移：先展示迁移摘要，用户确认后导入 SQLite，再核对交易所；核对通过后才允许继续交易。
- 随时可以预览迁移摘要，但只有当前实例全部任务停止后才能执行导入。
- 首版只导入旧订单状态及恢复其管理所需的关联数据，不导入旧日志，不额外扩展历史成交导入范围。
- 重复导入时跳过完全相同的记录；发现冲突则取消整批导入并展示差异，不保留本批部分导入结果。
- 导入且交易所核对通过后，对应任务全部保持暂停，由用户逐个手动启动；旧数据迁移不套用重启时自动恢复此前运行任务的规则。
- 旧数据已导入 SQLite 但部分订单无法通过交易所核对时，整批保持待核对，全部通过后才允许逐个手动启动；不先放行其中已通过核对的任务。此规则适用于导入后的核对阶段，导入时发现记录冲突仍取消整批导入。
- 旧订单没有新程序客户订单标识时，若账户、交易所订单 ID 及关键订单信息均核对一致，认定为迁移订单并继续管理，不额外要求逐单人工确认。无法确认归属的订单仍只展示，不自动接管。
- 导入字段映射、关键核对字段、旧订单与任务及两层 Intent 的关联，以及整批导入的事务与失败恢复实现待实施细化；迁移范围、重复导入与冲突处理原则已确认。
