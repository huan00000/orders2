# S2 领域与持久化基础

实施日期：2026-09-20。范围限于阶段计划 S2；以下为已写入的代码与设计边界，编译和测试尚待 GitHub Actions 执行。本阶段没有可运行的后台/TUI 或交易所适配器。

## 文件与依赖

- `CMakeLists.txt`：C++20、CMake 3.20+、SQLite 3.35+，构建 `orders2_core` 与一个 CTest 测试可执行文件。SQLite 使用系统开发包，不下载浮动源码依赖。配置保存使用 Linux/POSIX 文件接口；目标为首版 Linux amd64/arm64，不支持 Windows 原生编译。
- `include/orders2/domain.h`、`src/domain/order_state.cpp`：任务、目标、操作、订单状态及事件。金额、成交数量和价格在表内保持文本，不引入浮点交易计算；配置的时间间隔允许有限正数。
- `include/orders2/database.h`、`src/storage/database.cpp`：SQLite RAII、绑定参数、事务回滚和扩展错误码。
- `include/orders2/store.h`、`src/storage/store.cpp`：表结构 v1、约束、操作预写/发送/结果保存、订单历史、配置编辑门禁。
- `include/orders2/config.h`、`src/config/config.cpp`：旧 `.env` 格式、环境覆盖、保存校验与最近一份备份。
- `tests/foundation_test.cpp`：13 组云端测试源码，使用虚拟凭据、临时数据库及发送回调，不调用网络。

依赖选择已参考官方 [CMake FindSQLite3 文档](https://cmake.org/cmake/help/v4.3/module/FindSQLite3.html)、[SQLite 事务文档](https://www.sqlite.org/lang_transaction.html)和[部分索引文档](https://www.sqlite.org/partialindex.html)。CMake 对新旧 SQLite 导入目标名进行了兼容处理；构建版本最终由 S6 云端环境记录。

## SQLite 表与约束

| 表 | 用途及约束 |
| --- | --- |
| tasks | 账户、品种、方向、当前状态与期望状态；非 stopped 的任务占用唯一活动名额 |
| goals | 关联任务；active/paused 的目标合计最多一个 |
| operations | 全局唯一 Intent ID、目标关联、操作类型、请求摘要、客户标识或撤单对象、阶段、完整 Intent 与结果；prepared/sending/unknown 合计最多一个 |
| orders | 与创建操作一对一；当前状态与更新时间 |
| state_history | 订单及操作状态变化的时间、原因和来源；订单状态与历史同事务保存 |
| fills / positions | 精确数值文本、交易所成交标识及持仓快照；S3/S4 接入写入与核对 |
| manual_actions / logs | 人工操作及普通日志的表基础；S4/S5 接入，尚未实现保留清理 |
| runtime_metadata | 后续游标及恢复元数据的存放位置 |

所有连接开启外键、WAL、FULL 同步，写事务使用 `BEGIN IMMEDIATE`。业务冲突通过唯一/检查/外键约束拒绝，防重复判断与预写在同一事务内完成；不使用先查后在另一事务插入的方式。

普通数据库文件的父目录由后续后台创建，本阶段不创建真实运行数据库。测试内存数据库允许 SQLite 的 memory journal 行为。未知 schema 版本拒绝打开，不自动降级；数据库完整性检查、备份恢复和完整迁移版本机制在 S4 衔接。

## 发送时序与崩溃窗口

1. 检查任务/目标允许新操作；已有相同 Intent ID 时核对请求摘要与关联字段，返回已有记录，不调用发送回调；同 ID 内容不同则拒绝。
2. 提交最小预写：ID、父目标、类型、请求摘要、客户标识/撤单对象、时间与 prepared 阶段。创建订单时同时保存 pending_submit 订单和初始历史。此时完整 Intent 与结果为空。
3. 另一个事务提交 sending 阶段和 submitting 订单历史；撤单同时将已确认归属的订单置为 cancel_pending。
4. 两次提交均成功后才调用发送函数；网络期间不保持 SQLite 写事务。
5. 执行后在一个事务中保存完整 Intent、结果、订单/操作状态与历史。明确拒绝暂停父目标和任务；未知结果进入核实，父目标暂停。

prepared、sending、unknown 都是恢复扫描对象。即使实际崩溃发生在发送之前，也不依据本地阶段推定“肯定没发”；重启后相同 ID 仍不重发。确认未成功的交易所证据由 S3/P04 定义，本阶段没有“查询不到就失败”的入口。

创建响应缺订单 ID、发送异常均保留未知；异常对象原文不存库，避免泄露传输层敏感信息。回调返回内容与完整 Intent 仍必须由后续适配器脱敏，不能把账户密钥或原始带密钥 HTTP 数据传入。

撤单的 HTTP 接收响应不能结束操作。只有适配器提供已核对终态的 `cancellation_confirmed` 才能记录撤销完成，否则操作仍为 unknown、订单仍为 cancel_pending。取消中发生部分成交保持取消中，最终成交允许转 filled。该布尔值是内部适配契约，不是 TUI 人工确认入口；交易所证据验证留在 S3。

本阶段状态机不把 `success` 字符串直接解释为 filled，不提供目标成功完成的业务入口。P03 仍为 `<待确认最终完成判据>`，不能因为某个操作完成便结束父目标。

## 故障与后续服务边界

- 写入或提交发生存储异常时，在内存中阻止该账户后续写入/发送；磁盘坏时不依赖再次写库才能实现阻断。预留 ID/任务唯一性冲突作为正常业务错误处理；保存已取得的交易结果失败则阻断账户，包括约束错误。
- 已提交的发送记录保留，查询已有记录不要求解除阻断；不自动重试下单，不发撤单来处理存储故障。当前没有自动清除阻断的方法。
- S2 的阻断是当前 Store 进程内的交易门禁；不等于 S4 的完整账户任务停止、只读查询、TUI 状态展示或存储恢复流程。S4 必须在每次启动先核对、再决定任务能否运行，并实现手动检查后逐个恢复；不能直接把数据库里的 running 任务投入交易。
- Store 假设一个后台负责该实例所有写入。互斥锁保护进程内数据库调用，但发送期间会释放锁；S4 必须串行处理交易发送与用户任务命令、实现暂停/停止优先以及同宿主机账户互斥。不要把此基础库作为可并行调用的完整调度器。
- `dispatch` 的预写时间由调用者注入，响应后的记录时间另取 UTC 系统时钟（测试可注入假时钟）。S4 的核实倒计时使用独立单调时钟，不从预写时间推算完整网络时长。
- `resolve` 只记录肯定证据后的结果，不恢复运行；S4 负责 5 分钟核实、30 秒恢复倒计时、用户取消与超时转人工。

## 配置与 P06 实施草案

延续 `.env` 的 `API_KEY`、`API_SECRET`、`GHCR_IMAGE`；按第一个等号切分，去除边缘引号，环境优先。不引入 shell 执行、变量展开或行内注释解释。读取兼容旧文件中无等号行的忽略行为；编辑保存使用更严格的语法、重复键及引号检查。空部署读取可以没有密钥；保存账户配置必须具备非空密钥字段，实际启动交易时 S3/S4 再校验凭据。

本阶段新增的参数键为实施命名，可后续调整，默认值对应已确认需求或旧源码：

| 参数 | 默认值 |
| --- | --- |
| POLL_INTERVAL_SECONDS / REQUEST_TIMEOUT_SECONDS | 60 / 20，有限正数 |
| LOG_RETENTION_DAYS | 30；0 表示永久保留 |
| TRADE_RETENTION_DAYS / INTENT_RETENTION_DAYS / STATE_RETENTION_DAYS / MANUAL_RETENTION_DAYS | 0，永久保留 |
| BACKUP_INTERVAL_SECONDS / SCHEDULED_BACKUP_COUNT / UPGRADE_BACKUP_COUNT | 3600 / 24 / 5 |

多账户组织草案：每个账户保留一个同格式文件，由后台账户映射选择路径；不能用文件名或 API key 当成最终账户身份。账户身份仍属 P05/S4，尚未建立多账户配置管理入口。

建议宿主机 `config/` 目录挂载为容器 `/config`，每个账户文件的最近一份备份紧邻原文件，例如 `.env.bak`。数据库仍建议 `data/orders2.sqlite`，定时/升级备份分别在 `data/backups/scheduled`、`data/backups/upgrade`；这些挂载及数据库备份路径未在本阶段部署。

保存持有实例互斥锁与 SQLite 写事务，确认所有任务 stopped 后才进行文件操作。先校验，创建同目录 0600 临时文件，写入并 fsync；旧文件另写为临时备份并替换 `.bak`，再原子替换配置并同步目录。必须挂载配置目录，不能依赖直接绑定单个文件后的替换行为。

校验、临时写入或备份失败时原文件不变；若 rename 已成功但随后目录同步或 SQLite 事务收尾报错，文件可能已更新，应重新读取确认，不能声称此类故障也完成了跨文件/数据库回滚。本阶段不把配置内容写入数据库，配置备份和数据库备份分别管理。
